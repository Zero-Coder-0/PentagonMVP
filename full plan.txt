Getting a bird's-eye view of your Supabase schema—including the data, Row Level Security (RLS) policies, and table structures—is a smart move for auditing or debugging.

While SQL results usually come back in separate tabs, I’ve put together a **"Master Audit Script"** you can paste into the Supabase SQL Editor. It pulls your tables, their RLS status, and the specific policies attached to them into one clean list.

### 1. The Audit Command

Copy and paste this into your **SQL Editor** to see exactly how your security is configured:

```sql
SELECT 
    schemaname, 
    tablename, 
    rowsecurity AS rls_enabled,
    (SELECT count(*) FROM pg_policies p WHERE p.schemaname = t.schemaname AND p.tablename = t.tablename) AS policy_count,
    array_agg(p.policyname) AS policy_names,
    array_agg(p.cmd) AS actions, -- SELECT, INSERT, UPDATE, DELETE
    array_agg(p.roles) AS roles
FROM pg_tables t
LEFT JOIN pg_policies p ON t.schemaname = p.schemaname AND t.tablename = p.tablename
WHERE t.schemaname = 'public'
GROUP BY schemaname, tablename, rowsecurity;

```

---

### 2. Deep Dive: Getting Everything Else

If you need to go beyond just "seeing" and actually want to **export** or view the full definitions, here is how to handle the different parts of your request:

* **For Table Structures & Columns:**
If you want to see column types and whether they allow nulls, run:
```sql
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
ORDER BY table_name;

```


* **For the Policies' Logic:**
The first script tells you the names, but this one shows you the **actual code** (the `USING` and `WITH CHECK` expressions) that restricts the data:
```sql
SELECT tablename, policyname, permissive, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public';

```


* **For the Actual Data:**
SQL doesn't allow a single `SELECT *` to grab every row from every table into one view (because column structures differ). However, the fastest way to get your data out is:
1. Go to the **Table Editor** in the Supabase Sidebar.
2. Click **Export to CSV** on your main tables.



---

### 3. A Quick Security Health Check

When you run the audit script above, look for these **Red Flags**:

* **`rls_enabled` is `false**`: This means the table is public to the world if someone has your API key.
* **`policy_count` is `0` while RLS is `true**`: This means all access is denied (even to authenticated users).
* **`roles` includes `public**`: Ensure this is intentional (usually only for read-only blog posts or landing pages).

### 4. Need a full Schema Dump?

If your goal is to move this data or back it up entirely, the SQL Editor isn't actually the best tool. Instead, you should use the **Supabase CLI** from your local terminal:

```bash
supabase db dump --local > schema_backup.sql

```

This generates a single file containing every table creation script, every RLS policy, and every trigger in your project.

To get a complete overview of all schemas, tables, and security policies across your entire database, you can run a unified audit script in the **Supabase SQL Editor**.

In PostgreSQL, objects like tables and functions are organized into namespaces called **schemas**. While the `public` schema is where most of your data usually lives, system schemas (like `auth` or `storage`) and custom ones (like `pgbouncer` in your screenshot) also exist.

### 1. The Global Audit Command

Copy and paste this into your **SQL Editor** to see every table across every schema, its Row Level Security (RLS) status, and the count of policies attached to it.

```sql
SELECT 
    n.nspname AS schema_name,
    c.relname AS table_name,
    CASE 
        WHEN c.relrowsecurity THEN 'ENABLED' 
        ELSE 'DISABLED' 
    END AS rls_status,
    (SELECT count(*) FROM pg_policies p WHERE p.schemaname = n.nspname AND p.tablename = c.relname) AS policy_count,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema', 'pg_toast') -- Exclude internal system schemas
  AND c.relkind = 'r' -- Only show regular tables
ORDER BY schema_name, table_name;

```

---

### 2. Breakdown of Your Specific Schemas

Based on your screenshot, here is what those schemas generally contain:

* **`public`**: This is your main application data. RLS should almost always be **enabled** here.
* **`auth`**: Managed by Supabase. It stores user data, identities, and audit logs. **Do not modify** these tables directly.
* **`storage`**: Contains metadata for your uploaded files and buckets.
* **`pgbouncer`**: Related to connection pooling and infrastructure.
* **`realtime`**: Manages the publication of database changes to your clients.

---

### 3. Seeing the Detailed Restrictions (RLS Policies)

If you see a table in the first query with a `policy_count` greater than 0, use this command to see the **actual logic** (the code) that restricts who can see what:

```sql
SELECT 
    schemaname, 
    tablename, 
    policyname, 
    permissive, 
    roles, 
    cmd AS operation, -- SELECT, INSERT, etc.
    qual AS using_expression, 
    with_check AS check_expression
FROM pg_policies
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY schemaname, tablename;

```

---

### 4. How to Get "Everything" Locally

If you need to see every single detail (triggers, functions, constraints, and data) in one massive text file, the SQL Editor isn't enough. You should use the **Supabase CLI** from your computer:

* **For the Schema (Structure/Policies):** `supabase db dump --local > full_schema.sql`
* **For the Data (Rows):** `supabase db dump --data-only > all_data.sql`

### Quick Security Check

> **Warning:** If the audit script shows `rls_status` as **DISABLED** for any table in your `public` schema, that data is potentially exposed to the internet via your API key. You should run `ALTER TABLE <table_name> ENABLE ROW LEVEL SECURITY;` for those tables.
